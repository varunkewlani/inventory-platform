# ADR-004 — Kafka vs a Simpler Broker (RabbitMQ / Redis Streams)

**Decision:** Kafka, one topic (`order-events`), two independent consumer groups (`audit-worker-group`, `notification-worker-group`).

**Reason:** Primarily familiarity under a hard deadline — Kafka is a tool already used in production elsewhere, so no new operational concept had to be learned to ship this correctly in the time available. It also matches the assignment's own suggested architecture diagram exactly (Order Service → Message Broker → Audit Worker / Notification Worker as separate consumers), and Kafka's consumer-group model maps directly onto that fan-out: two consumer groups on the same topic each independently receive every message, which is precisely "the order event goes to both workers, and either one being slow or down doesn't affect the other."

**Honest trade-off:** For this project's actual scale (one topic, low volume, a single broker instance), RabbitMQ or Redis Streams would have been simpler to operate and would have worked equally well — Kafka's partitioning/replication/log-retention model is more machinery than this specific workload needs. The choice is defensible on familiarity and spec-alignment grounds, not because the workload demands Kafka specifically. If message volume or the number of distinct event types grew substantially, Kafka's log-based replay and partition-level ordering guarantees would start to pay for themselves; at today's scale, that's a future benefit, not a current one.

**What actually depends on this being async at all:** order creation and status updates never block on Kafka being available — `OrderServiceImpl` publishes a Spring `ApplicationEvent` inside its transaction, and only forwards to Kafka in an `AFTER_COMMIT` listener (see [ARCHITECTURE.md](ARCHITECTURE.md) and the Phase 4 handoff note). If Kafka is down, orders still succeed; only the audit-log entry and the real-time notification for that order are delayed until Kafka recovers.
